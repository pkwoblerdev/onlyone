# Стенд качества агентной работы

Первый срез: четыре сквозных сценария через настоящий `send-message` и агентный цикл.
Ответы модели в самопроверке даёт файл-сценарий (`ONECODE_PROVIDER_FILE`), сеть не нужна.

## Запуск

```bash
npm run bench:agent
```

Одна документированная команда. Полезные аргументы:

```bash
npm run bench:agent -- --scenario false-done --repeat 2
npm run bench:agent -- --timeout 60 --out ./tmp/quality-run
```

Оценка настоящей модели — только руками, со стендовым профилем (не личным):

```bash
npm run bench:agent -- --mode live --model <id> --profile <папка стендового профиля>
```

## Что проверяется

| Сценарий | Скрытая проверка |
|---|---|
| `file-result` | два файла точно по заданию; испорченный `data.json` отклоняется |
| `fix-after-check` | видимая `node verify.js` и скрытая проверка `add` сходятся |
| `interrupt-resume` | запись одна после прерывания и продолжения; опись знает о сделанном |
| `false-done` | собственный тест агента проходит, скрытая проверка ловит ложное «готово» |

Каждая попытка — свой временный Workspace и профиль. Скрытые проверки лежат в
`scripts/quality-bench/scenarios.cjs`, вне Workspace, и агенту не передаются. Это
изоляция файлов и ответов стенда, а не песочница ОС: сеть и браузер агента не ограничены.

## Отчёт

`report.json` в каталоге прогона: версия исходников, сценарий, модель, параметры,
результат проверки, заявление о завершении, число запросов, токены, длительность и
причина остановки. Неизвестные токены — `null`, не ноль. Ошибка агента, ошибка стенда
и отказ провайдера различаются полем `verdict`.

Повторы (`--repeat`) — только начальная оценка шума; два запуска не доказывают пользу
изменения. Тайм-аут попытки снимает дочернее дерево процессов.

## Надёжность первого среза

- `--out` должен указывать на новый каталог: повторный запуск не перезаписывает старые
  попытки, файлы, журнал запросов или отчёт. Без `--out` создаётся новый временный каталог.
- `--repeat` — целое от 1 до 100; `--timeout` — от 10 до 3600 секунд на запуск.
  Ошибочные значения и неизвестные сценарии отклоняются до открытия окна.
- В live копируются только `1code-settings.json` и `Local State` из явно выбранного
  стендового профиля. История, браузерные cookies, задания и прочие каталоги не копируются.
  Стандартные личные профили APPDATA/1code и APPDATA/onlyone запрещены. Произвольный
  перенесённый личный профиль автоматически распознать нельзя — используйте отдельный профиль.
- Отчёт атомарно обновляется после каждой попытки; `completed: false` означает незавершённый
  прогон. `summary.executionOk` показывает отсутствие сбоев стенда/провайдера; `summary.ok`
  в self требует ожидаемого исхода каждого сценария, а в live — успешного результата всех задач.
- Запросы и токены суммируются по обоим запускам продолжения. Если хотя бы часть расхода
  неизвестна, итоговое значение `null`. `durationMs` включает подготовку/ожидание/проверку;
  `executionDurationMs` содержит время запусков приложения.
- Проверка файлов не зависит от формулировки ответа. `completionClaim` — лишь текстовая
  эвристика заявления о завершении, не доказательство успеха. Сырые stderr провайдера не
  включаются в переносимый отчёт.
- Проверки созданного JS работают в отдельных процессах с тайм-аутом 2 секунды и
  ограниченным выводом. `process.exit(0)` до завершения скрытой проверки не считается успехом.
  Это защита процесса стенда от зависания, а не изоляция ОС от враждебного кода.
- Продолжение допускается только после наблюдённого прерывания и успешного запроса остановки
  с подтверждённым выходом корневого процесса. Результат остановки записан в `launches`;
  независимо отделившиеся потомки не гарантированно охвачены.

Дополнительная адресная проверка: `node tests/test-quality-bench-reliability.cjs`.
Настоящие модели, защищённый контрольный набор и A/B остаются отдельными этапами.

## Сравнение сохранённых прогонов

```bash
npm run bench:compare -- --kind aa --out aa.json run-a/report.json run-b/report.json
npm run bench:compare -- --kind ab --out ab.json baseline/report.json candidate/report.json
```

Сравнение не вызывает модель. Нужны завершённые отчёты с чистой идентифицированной
ревизией и одинаковым `suiteDigest`: отпечатком заданий, проверок и оконных сценариев
стенда. Старые отчёты без отпечатка нужно получить заново. Выходной файл должен быть
новым; существующее доказательство не перезаписывается.

Попытки сопоставляются по сценарию и номеру повтора. Нельзя молча отбросить пропущенную
пару, смешать self/live, разные задания, условия допуска/дедлайна или ошибки стенда и
провайдера. Для A/A также совпадают ревизия и запрошенная модель. В A/B смена ревизии
или модели видна в отчёте. Неизвестный расход остаётся null и в сумме, и в разнице.

Вывод содержит исходы пар, число выполненных задач и разницу запросов, токенов и
времени. Это описательные наблюдения: `effectProven: false`. Self обозначен как проверка
стенда на сценарных ответах. Совпадение всех настроек, фактической модели, окружения и
эффекта статистически не доказывается; сравнение не принимает эксперимент автоматически.

## Уроки проекта (проверка пользы, а не вторая лаборатория)

Шесть задач `lesson-*` проверяют подачу уроков тем же стендом: проект и уроки
кладутся в копию профиля попытки (проект — в настройки, уроки — зондом в настоящее
шифрованное хранилище теми же действиями, что у человека), `turn.cjs` передаёт
`projectId`, скрытая проверка читает дамп запроса провайдера и состояние хранилища.
Ответы сценарного провайдера выдаются по метке: ключевой ответ приходит, только
когда текст урока есть в запросе. Это проверка стенда, не качества модели.

| Сценарий | Критерий |
|---|---|
| `lesson-applied` | включённый подходящий урок своего проекта есть в запросе, результат соответствует уроку |
| `lesson-ignored` | включённый, но неподходящий урок не подан; задача решена без него |
| `lesson-isolation` | в проекте Б действует только урок Б; урок проекта А не подан и его файл не создан |
| `lesson-corrected` | после исправления старая версия отозвана, новая ждёт включения: в запросе нет ни одной |
| `lesson-corrected-enabled` | после включения человеком в запросе только новая версия, старая отсутствует |
| `lesson-stale` | применимый устаревший урок подан вместе с оговоркой о приоритете; результат следует текущей просьбе, файла устаревшего правила нет |

Сравнение условий «без уроков / с уроками»:

```bash
npm run bench:agent -- --lessons off --out run-off
npm run bench:agent -- --lessons on --out run-on
npm run bench:compare -- --kind lessons --out lessons.json run-off/report.json run-on/report.json
```

`--lessons` по умолчанию `on`; профиль отличается только набором уроков, проект и
просьба те же. `--kind lessons` требует пары off→on, одинаковые проект, ожидания
уроков, условия запуска, ревизию и модель, сохраняет исходы, запросы, токены, время
и причины неуспеха. Задачи без уроков перечислены в `excluded`, а не отброшены
молча. Ошибка провайдера — отдельный исход пары (`provider-error`), неизвестный
расход остаётся `null`, а не нулём. Самопроверка на сценарном провайдере говорит
только о работе стенда: `effectProven: false`, `configurationFullyVerified: false`.
В live дампа запроса нет, поэтому блок уроков берётся из зонда хранилища и это
честно записано в `lessons.promptSource`.

## Защищённые задачи (браузер, документ, Desk)

Три сценария добавлены к четырём первым (теперь семь). Все идут на сценарном
провайдере, без сети и аккаунтов; скрытые проверки — в `scripts/quality-bench/tasks.cjs`,
вне Workspace попытки.

| Сценарий | Что делает агент | Скрытая проверка и ограничения |
|---|---|---|
| `browser-local-page` | открывает локальную страницу стенда, жмёт «Показать код подтверждения», пишет код в `answer.txt` | код живёт только в памяти стенда и отдаётся на POST с одноразовой меткой; сервер ведёт журнал нажатий. Ошибка: неверный код, код не показан, нажата «Удалить заявку», отклонённый спрос на чужой адрес |
| `document-requirements` | правит `docs/release.md` по нескольким требованиям | структура документа сверяется по разделам (окончания строк и пустые строки не важны); чужие разделы, новые разделы, резервные копии, правка других файлов — ошибка |
| `desk-layout` | через `desk_workspace` убирает блок и задаёт раскладку двух блоков | раскладка читается отдельным зондом из настоящего зашифрованного хранилища Desk после хода (`tests/quality-bench/desk-probe.cjs`), а не из слов агента; файлы создавать нельзя |

Отрицательные ограничения проверяются снимком дерева: лишние файлы в Workspace, правка
чужих, удаление, запись в соседнюю папку `outside/` попытки и новые файлы рядом с
Workspace. В окне стенд «отвечает за человека»: разрешает только адрес страницы задачи,
любой другой спрос отклоняет, и отказ роняет проверку. Отчёт хранит `falseDone` (агент
заявил о завершении, проверка не прошла) и `approvals: {asked, denied}`; `null`, если
отчёта окна не было. `suiteDigest` теперь охватывает задачи, страницу, зонд Desk и оба
оконных сценария.

**Границы.** Это изоляция файлов и ответов, не песочница ОС: агент с `run_command` может
обратиться к странице или файлам иначе, и проверка увидит только то, что дошло до неё.
Сценарные ответы проверяют сам стенд, не качество модели. Условия первых четырёх
сценариев без ограничений не менялись.

## Повторы A/A

```bash
npm run bench:aa -- --runs 3 --out D:/tmp/aa-self
npm run bench:aa -- --runs 3 --out D:/tmp/aa-live --mode live --model <id> --profile <стендовый профиль>
```

Команда запускает стенд `--runs` раз (по умолчанию 2, до 20) в `run-1…`, затем пишет
`aa-summary.json`: по сценарию — число пройденных, стабильность исхода, ложные «готово»,
разброс времени, запросов и токенов (`null`, если расход неизвестен). Источник, набор
задач, модель и условия должны совпадать — иначе сводка отказывает. `--out` — новый
каталог.

**Два прогона — лишь начальная оценка шума**, а не основание для вывода. Число повторов
уточняют по наблюдаемому разбросу; сводка всегда `effectProven: false`.
